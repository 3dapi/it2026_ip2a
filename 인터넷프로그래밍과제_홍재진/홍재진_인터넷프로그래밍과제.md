## 1. 개요

### 1.1 과제 목적

본 과제의 목적은 실제 게임 화면에서 확인할 수 있는 기능과 정보를 근거로 게임 서버의 데이터베이스 구조를 추론하고 설계하는 것이다. 수업에서 다룬 개체, 속성, 키, 관계, 카디널리티를 실제 게임에 적용하였으며, ERD는 Crow's Foot 표기법으로 작성하였다. 분석 대상 4종 모두 과금 요소가 있으므로 결제와 재화 관련 데이터 구조도 함께 분석하였다.

### 1.2 분석 대상 게임

장르와 과금 방식이 비슷한 게임은 데이터베이스 구조도 비슷하게 나타나므로, 비교가 가능하도록 서로 다른 유형의 게임을 선정하였다. 대전 게임, MMORPG, 가챠 게임, 카드 대전 게임을 각각 1종씩 선택하였다.

| 게임 | 장르 | 개발/서비스 | 플레이 단위 | 과금 모델 |
| --- | --- | --- | --- | --- |
| 리그 오브 레전드 | MOBA (5:5 팀 대전) | Riot Games | 매치(한 판) | 부분 유료: RP로 스킨/챔피언 구매 |
| 메이플스토리 | 2D 횡스크롤 MMORPG | 넥슨 | 캐릭터 성장(지속형) | 부분 유료: 캐시샵, 확률형 아이템(큐브 등) |
| 원신 | 오픈월드 액션 RPG | HoYoverse | 계정 성장 + 수집 | 부분 유료: 기원(가챠), 월정액, 패스 |
| 클래시 로얄 | 실시간 카드 대전 | Supercell | 짧은 대전 + 카드 수집 | 부분 유료: 보석, 시즌 패스, 상점 상품 |

### 1.3 분석 방법

분석은 다음 순서로 진행하였다.

- 프로필, 인벤토리, 상점, 전적, 길드(클랜) 화면에 표시되는 정보를 기능별로 정리하였다.
- 여러 화면에 반복해서 나타나는 대상(계정, 캐릭터, 아이템 등)을 개체로, 그 대상을 설명하는 값을 속성으로 도출하였다.
- 각 개체를 구분할 수 있는 값을 기본키로, 다른 개체를 참조하는 값을 외래키로 지정하였다.
- "한 계정은 여러 캐릭터를 생성할 수 있다"와 같이 화면에서 확인되는 사실을 근거로 관계와 카디널리티를 정하였다.
- 다대다(M:N) 관계는 연결 테이블을 두어 1:N 관계 두 개로 분해하였다.
- 모든 플레이어가 공유하는 원본 데이터(마스터 데이터)와 플레이어별 보유 데이터(인스턴스 데이터)를 분리하였다.

게임사의 실제 데이터베이스 구조는 공개되어 있지 않으므로, 본 보고서의 설계는 관찰에 근거한 추론이다. 다만 리그 오브 레전드, 메이플스토리, 클래시 로얄은 공식 개발자 API를 제공하므로, API 문서에 명시된 데이터 항목을 추론의 근거로 활용하였다. API로 조회되는 항목은 서버에 저장되어 있는 데이터이기 때문이다.

### 1.4 표기 규칙

키 표기

| 표기 | 의미 |
| --- | --- |
| PK | 기본키 (Primary Key). 행을 하나로 구분하는 값 |
| FK | 외래키 (Foreign Key). 다른 테이블의 기본키를 가리키는 값 |
| PK, FK | 기본키이면서 외래키 (주로 연결 테이블, 1:1 관계) |
| UK | 유일키 (Unique Key). 중복되면 안 되는 값 |

Crow's Foot 관계 기호 (텍스트 표기)

| 기호 | 의미 | 예시 |
| --- | --- | --- |
| \|\|--\|\| | 1 : 1 (양쪽 모두 정확히 하나) | 계정 - 지갑 |
| \|\|--o{ | 1 : 0..N (하나가 0개 이상을 가짐) | 계정 - 캐릭터 |
| \|\|--\|{ | 1 : 1..N (하나가 1개 이상을 가짐) | 매치 - 참가자 |
| \|\|--o\| | 1 : 0..1 (하나가 최대 하나를 가짐) | 캐릭터 - 길드 가입 정보 |
| \|o--o{ | 0..1 : 0..N (선택적 소속) | 장착 캐릭터 - 성유물 |

ERD 이미지는 MySQL Workbench로 작성하였고, 이미지 아래에 관계를 텍스트로 함께 정리하였다. 텍스트 표기는 "왼쪽 개체 기호 오른쪽 개체 : 설명" 순서로 읽는다.

## 2. 게임 1 - 리그 오브 레전드

### 2.1 게임 소개

리그 오브 레전드(LoL)는 5명씩 두 팀이 상대 넥서스를 파괴하는 MOBA 게임이다. 매치가 끝날 때마다 전적이 기록되고, 랭크 게임은 시즌별로 티어와 LP가 기록된다. 과금으로 캐릭터 능력이 강해지는 요소는 없으며, 챔피언과 스킨을 RP로 구매하는 구조이다.

설계 시 고려 사항

- Riot ID(이름#태그)는 변경이 가능하므로 기본키로 사용하지 않고 별도의 account_id를 기본키로 지정하였다. 이름과 태그의 조합은 중복될 수 없으므로 유일키를 설정하였다.
- 챔피언과 스킨 정보는 모든 플레이어가 공유하는 마스터 데이터이다. 플레이어별 보유 정보는 OWNED_CHAMPION, OWNED_SKIN 테이블로 분리하였다.
- 한 매치에는 10명이 참가하고 한 계정은 여러 매치에 참가하므로 계정과 매치는 M:N 관계이다. 이를 MATCH_PARTICIPANT 테이블로 분해하고, K/D/A처럼 특정 매치에서의 개인 기록을 이 테이블에 저장하였다.
- 아이템을 item1~item6 컬럼으로 저장하면 아이템별 집계가 어렵다. 따라서 PARTICIPANT_ITEM 테이블로 분리하여 정규화하였다.
- 친구 관계는 계정이 다른 계정을 참조하는 구조이므로 ACCOUNT를 두 번 참조하는 자기 참조 관계로 설계하였다.

### 2.4 관계와 카디널리티

| 관계 | 카디널리티 | 근거(화면에서 확인되는 사실) |

| ACCOUNT - MATCH_PARTICIPANT | 1 : 0..N | 한 계정의 전적은 여러 판으로 쌓인다 |
| CHAMPION - MATCH_PARTICIPANT | 1 : 0..N | 참가자는 매치에서 챔피언 하나를 사용한다 |
| MATCH_PARTICIPANT - PARTICIPANT_ITEM | 1 : 0..N | 최종 아이템은 최대 7칸이다 |
| MATCH_PARTICIPANT - PARTICIPANT_RUNE | 1 : 1..N | 참가자마다 룬 페이지 하나(여러 룬)를 고른다 |
| SUMMONER_SPELL - MATCH_PARTICIPANT | 1 : 0..N | 참가자는 소환사 주문 2개를 고른다 (FK 2개) |
| ACCOUNT - RANKED_ENTRY - SEASON | M : N | 계정마다 시즌과 큐 종류별로 랭크 기록이 있다 |

| ACCOUNT - WALLET | 1 : 1 | 계정마다 RP와 BE 잔액이 하나씩 있다 |
| ACCOUNT - RP_PURCHASE | 1 : 0..N | 결제 내역이 여러 건 쌓인다 |
| RP_PACKAGE - RP_PURCHASE | 1 : 0..N | 같은 상품을 여러 번 살 수 있다 |
| ACCOUNT - STORE_TRANSACTION | 1 : 0..N | 상점 구매 내역 |

### 2.5 과금 데이터 구조

LoL의 과금은 현금으로 RP를 충전한 뒤 RP로 상품을 구매하는 2단계 구조이다.

- RP를 충전하면 RP_PURCHASE에 결제 금액, 결제 수단, 지급된 RP가 기록되고 WALLET의 RP 잔액이 증가한다.
- 챔피언이나 스킨을 구매하면 STORE_TRANSACTION에 기록이 남고, 보유 테이블(OWNED_CHAMPION, OWNED_SKIN)에 행이 추가된다.
- 플레이로 획득하는 블루 에센스(BE)로도 챔피언을 구매할 수 있으므로, currency_type 컬럼으로 RP와 BE를 구분하였다.
- 상점에 환불 기능이 있으므로 구매 기록은 삭제하지 않고 refunded 값으로 환불 여부를 표시하였다. 잔액만 저장할 경우 환불 처리의 근거가 남지 않기 때문이다.
- product_type과 product_id로 챔피언, 스킨, 아이콘을 하나의 테이블에서 참조하도록 하였다. 다만 이 방식은 외래키 제약을 걸 수 없다는 한계가 있으며, 별도의 상품 테이블을 두는 방법으로 개선할 수 있다.

### 2.6 ERD (Crow's Foot 표기)

## 3. 게임 2 - 메이플스토리

### 3.1 게임 소개

메이플스토리는 2003년부터 서비스 중인 2D 횡스크롤 MMORPG이다. 넥슨 계정 하나로 여러 월드에 캐릭터를 생성할 수 있으며, 캐릭터는 직업을 선택하여 레벨을 올리고 장비를 강화한다. 같은 이름의 장비라도 스타포스 수치와 잠재능력 옵션이 개별적으로 다르기 때문에 아이템 데이터 구조가 복잡하다. 플레이어 간 경매장 거래가 있으며, 캐시샵과 큐브 등 확률형 아이템으로 과금한다.

설계 시 고려 사항

- 계정 - 월드 - 캐릭터의 3단 구조로 설계하였다. 월드가 다르면 아이템을 주고받을 수 없으므로 CHARACTER에 world_id를 두었다. 캐릭터명은 같은 월드 안에서 중복될 수 없으므로 (world_id, name)에 유일키를 설정하였다.
- 같은 아이템이라도 강화 수치가 개별적으로 다르기 때문에 아이템 원본(ITEM)과 실제 보유 아이템(ITEM_INSTANCE)을 분리하였다. 소비 아이템처럼 속성이 동일한 아이템은 수량(quantity)으로 관리한다.
- 잠재능력은 잠재 3줄과 에디셔널 3줄로 구성된다. 이를 컬럼 6개로 저장하면 특정 옵션을 가진 장비를 검색하기 어려우므로 ITEM_POTENTIAL 테이블로 분리하였다.
- 직업은 1차, 2차, 3차 순으로 전직하는 계층 구조이므로 JOB 테이블이 이전 직업을 참조하는 자기 참조 관계로 설계하였다.
- 경매장은 등록(AUCTION_LISTING)과 거래 체결(AUCTION_TRADE)을 분리하였다. 판매되지 않고 기간이 만료되거나 수량 일부만 판매되는 경우를 표현하기 위해서이다.

### 3.5 과금 데이터 구조

메이플스토리의 과금은 재화(캐시)는 계정 단위로, 구매한 아이템은 캐릭터 단위로 관리되는 구조이다.

- 넥슨캐시는 같은 계정의 모든 캐릭터에서 동일하게 표시되므로 계정 단위(CASH_WALLET)로 저장하였다. 충전 기록은 CASH_CHARGE에 저장한다.
- 캐시샵에서 상품을 구매하면 CASH_PURCHASE에 기록되고, 받는 캐릭터의 인벤토리에 아이템이 생성된다. 선물하기 기능이 있으므로 구매 계정과 받는 캐릭터를 별도 컬럼으로 저장하였다.
- 큐브는 사용할 때마다 옵션이 무작위로 변경된다. 2024년 3월부터 확률형 아이템 정보 공개가 법적 의무가 되었고, 넥슨 Open API에서도 큐브 사용 결과를 조회할 수 있다. 이를 근거로 사용 기록이 저장된다고 판단하여 CUBE_USE_LOG 테이블을 설계하였다.
- 경매장 거래는 메소로 이루어지지만 거래 수수료가 부과되므로 거래 금액과 수수료를 함께 기록하였다.

## 4. 게임 3 - 원신

### 4.1 게임 소개

원신은 HoYoverse가 서비스하는 오픈월드 액션 RPG이다. 플레이어는 캐릭터를 수집하여 4인 파티를 구성하고, 캐릭터마다 무기 1개와 성유물 5개를 장착하여 육성한다. 캐릭터와 무기는 주로 "기원"이라는 가챠(뽑기)로 획득한다. 일정 횟수 안에 5성이 나오지 않으면 확정 지급하는 천장 시스템이 있으므로, 서버는 플레이어별 누적 뽑기 횟수를 저장해야 한다.

설계 시 고려 사항

- HoYoverse 계정 하나로 서버마다 다른 UID가 생성되며, 서버 간 데이터는 공유되지 않는다. 따라서 캐릭터와 아이템 데이터는 ACCOUNT가 아닌 PLAYER(uid)에 연결하였다.
- 같은 캐릭터를 중복 획득하면 캐릭터가 추가되지 않고 운명의 자리가 상승한다. 따라서 OWNED_CHARACTER의 (uid, character_id)에 유일키를 설정하고, 중복 획득 시 constellation 값을 증가시키도록 하였다.
- 무기는 같은 무기를 여러 개 보유할 수 있으므로 개별 인스턴스(WEAPON_INSTANCE)로 저장하였다. 캐릭터는 무기를 반드시 1개 장착하며, 무기는 최대 1명에게만 장착된다.
- 성유물의 부옵션은 1~4줄로 개수가 다르고 강화 시 추가되므로 ARTIFACT_SUBSTAT 테이블로 분리하였다.
- 레진은 시간 경과에 따라 자동으로 회복된다. 값을 매번 갱신하는 대신 마지막 갱신 시각(resin_updated_at)을 저장하고 조회 시점에 현재 값을 계산하는 방식으로 설계하였다.

### 4.5 과금 데이터 구조 (기원과 천장)

원신의 과금은 "결제 → 창세의 결정 → 원석 → 인연 → 기원"으로 이어지는 다단계 재화 전환 구조이다.

- 결제 시 TOP_UP_ORDER에 기록되고 WALLET의 창세의 결정이 증가한다. 상품별 첫 결제에는 2배 보너스가 적용되므로 보너스 적용 여부(is_first_bonus)를 함께 저장하였다.
- 창세의 결정을 원석으로, 원석을 인연으로 교환하면 WALLET의 해당 재화 값이 변경된다.
- 기원을 진행하면 결과가 WISH_LOG에 한 행씩 기록되고 PITY_STATE의 횟수가 갱신된다. 결과가 캐릭터이면 OWNED_CHARACTER가 생성되거나 운명의 자리가 상승하고, 무기이면 WEAPON_INSTANCE가 생성된다.
- 게임 내 기원 상세 안내에 따르면 캐릭터 이벤트 기원은 5성 기본 확률 0.6%, 최대 90회 안에 5성 확정, 4성은 10회마다 확정이다. 5성이 픽업 대상이 아니면 다음 5성은 픽업으로 확정되며, 이 상태를 is_guaranteed로 저장하였다. 무기 기원은 80회 천장과 "신의 궤도" 포인트가 별도로 존재한다.
- 캐릭터 이벤트 기원의 천장 횟수는 배너가 바뀌어도 유지되고, 무기 기원과 상주 기원은 각각 따로 누적된다. 따라서 PITY_STATE의 키를 banner_id가 아닌 기원 종류(pity_group)로 설정하였다.
- 기원 기록은 게임 내에서 최근 6개월분을 조회할 수 있다. 확률형 결과에 대한 문의와 분쟁에 대응해야 하므로 WISH_LOG는 삭제하지 않고 보관하는 로그 테이블로 설계하였다.
- 공월 축복(월정액)은 30일간 매일 원석을 지급하므로 SUBSCRIPTION에 시작일과 종료일을 저장하였다.

## 5. 게임 4 - 클래시 로얄

### 5.1 게임 소개

클래시 로얄은 Supercell이 서비스하는 실시간 카드 대전 게임이다. 플레이어는 카드 8장으로 덱을 구성하여 약 3분간 1:1 대전을 진행하고, 승리하면 트로피를 얻어 상위 아레나로 올라간다. 같은 카드를 모아 카드 레벨을 올리며, 클랜원 간 카드 기부와 클랜전 기능이 있다. LoL과 같은 대전 게임이지만 카드 수집과 클랜 협력 요소가 있다는 점에서 차이가 있다.

설계 시 고려 사항

- 플레이어 태그(#ABC123 형식)는 변경되지 않는 고유 값이며 친구 추가와 공식 API 조회에도 사용된다. 따라서 LoL과 달리 태그를 기본키로 사용하였다. 클랜 태그도 같은 이유로 CLAN의 기본키로 사용하였다.
- 카드는 개별 인스턴스가 아니라 카드 종류별 레벨과 보유 장수로 표시된다. 따라서 별도의 인스턴스 테이블 없이 (player_tag, card_id) 복합키로 설계하였다.
- 덱에는 카드 8장이 순서대로 들어가며, 같은 덱에 같은 카드를 중복해서 넣을 수 없다. 따라서 순서(position)를 기본키에 포함하고 카드에는 유일키를 설정하였다.
- 대전 기록이 PLAYER_CARD를 참조하면 카드 레벨이 오를 때 과거 대전 기록의 값도 함께 바뀐다. 이를 방지하기 위해 BATTLE_CARD에 대전 당시의 카드 레벨을 복사하여 저장하였다(스냅샷).
- 플레이어는 클랜에 하나만 가입할 수 있으므로 CLAN_MEMBER의 기본키를 player_tag 단일 컬럼으로 지정하여 중복 가입을 제약하였다.

| 관계 | 카디널리티 | 근거(화면에서 확인되는 사실) |
| --- | --- | --- |

| ARENA - CARD | 1 : 0..N | 카드는 특정 아레나에서 해금된다 |
| PLAYER - PLAYER_CARD - CARD | M : N | 플레이어는 여러 카드를 가지고, 같은 카드를 여러 플레이어가 가진다 |
| PLAYER - DECK | 1 : 1..N | 덱 슬롯 여러 개 |
| DECK - DECK_CARD | 1 : 8 (1..N) | 덱 하나는 카드 8장 |

| BATTLE - BATTLE_PARTICIPANT | 1 : 2..N | 1:1 대전은 2명, 2:2 대전은 4명 |

### 5.5 과금 데이터 구조

클래시 로얄의 과금은 현금 또는 보석으로 상점 상품을 구매하여 카드와 골드를 획득하는 구조이다.

- 현금 결제 시 PURCHASE에 플랫폼(App Store, Google Play)과 결제 금액이 기록된다. 보석 상품인 경우 WALLET의 보석이 증가한다.
- 상점 상품은 현금, 보석, 골드 중 하나로 구매하므로 테이블을 분리하지 않고 currency 컬럼으로 구분하였다.
- 상품 하나에 골드, 카드, 보석이 함께 포함되는 경우가 있으므로 SHOP_OFFER(상품)와 OFFER_ITEM(구성품)을 1:N으로 분리하였다. 구매 제한은 (player_tag, offer_id)별 구매 기록 수로 확인할 수 있다.
- 시즌 패스는 시즌별 무료/유료 여부와 진행 단계를 SEASON_PASS에 저장하였다.
- 과금으로 획득한 카드도 카드 레벨 상승에 사용되므로, LoL과 달리 과금이 대전 능력에 일부 영향을 주는 구조이다.

### 5.7 분석 정리

클래시 로얄 데이터베이스의 중심은 PLAYER_CARD와 BATTLE이다. 카드는 종류별로 한 행만 저장하므로 아이템 구조는 단순하다. 반면 대전 시간이 약 3분으로 짧아 대전 기록이 빠르게 누적된다. 또한 클랜 기부처럼 플레이어 간 카드를 주고받는 기능이 DONATION_REQUEST, DONATION 테이블로 구조화된다는 특징이 있다.

### 6.2 공통점

- 마스터 데이터와 인스턴스 데이터의 분리: 4종 모두 원본 데이터(챔피언, 아이템, 캐릭터, 카드)와 플레이어별 보유 데이터를 분리한다. 원본 데이터는 업데이트 시에만 변경되지만 보유 데이터는 플레이 중 계속 변경되기 때문이다.
- M:N 관계의 연결 테이블: 보유(플레이어-아이템), 참가(플레이어-매치), 진행(플레이어-퀘스트)은 모두 M:N 관계이다. 연결 테이블에는 획득 시각, 레벨, 매치 기록 등 관계 자체의 속성이 저장된다.
- 잔액과 거래 기록의 분리: 재화 잔액은 플레이어마다 하나이므로 1:1 지갑 테이블로 두고, 충전과 구매 기록은 별도의 1:N 테이블에 저장한다. 잔액만 저장하면 환불이나 결제 분쟁 시 근거를 확인할 수 없기 때문이다.
- 2단계 결제 구조: 4종 모두 "현금 → 게임 재화 → 상품" 순서로 과금이 이루어지므로, 결제 테이블과 재화 사용 테이블을 분리하여 설계하였다.

### 6.3 차이점

- 아이템 구조의 복잡도: 메이플스토리 > 원신 > 클래시 로얄 > LoL 순이다. 메이플스토리와 원신은 같은 아이템이라도 옵션이 개별적으로 달라 인스턴스 테이블이 필요하다. 클래시 로얄은 카드 종류별 한 행, LoL은 보유 여부만 저장한다.
- 기록형과 상태형: LoL과 클래시 로얄은 매치가 끝날 때마다 기록이 추가되는 기록형(INSERT 중심) 구조이다. 메이플스토리와 원신은 캐릭터의 현재 상태를 지속적으로 갱신하는 상태형(UPDATE 중심) 구조이다.
- 데이터 소유 단위: 게임 데이터의 기준이 메이플스토리는 캐릭터, 원신은 서버별 UID, LoL은 계정, 클래시 로얄은 플레이어 태그로 서로 다르다.
- 확률형 데이터: 원신은 천장 횟수처럼 다음 결과에 영향을 주는 상태 값을 저장해야 하므로 가챠 관련 구조가 가장 복잡하다. 메이플스토리는 큐브 결과 기록 중심이며, LoL은 확률형 과금 데이터가 거의 없다.
- 소셜 데이터: 클래시 로얄과 메이플스토리는 클랜·길드 관련 테이블의 비중이 크다. 원신은 혼자 진행하는 콘텐츠 위주이므로 소셜 관련 테이블이 거의 없다.

### 6.4 정리

게임의 핵심 콘텐츠에 따라 데이터베이스에서 비중이 큰 테이블이 달라진다. 대전 중심 게임은 매치 기록 테이블이, 성장·수집 중심 게임은 아이템 인스턴스와 옵션 테이블이 가장 크고 복잡하다. 또한 과금이 확률형 아이템과 연결될수록 결과 기록과 천장 상태를 정확하게 저장하는 구조가 필요하다. 따라서 게임 데이터베이스 설계는 해당 게임에서 가장 자주 누적되거나 변경되는 데이터를 먼저 파악하는 것에서 시작해야 한다.

## 7. 결론

4종의 게임을 분석한 결과, 장르는 달라도 데이터베이스의 기본 구성은 공통적이다. 계정(플레이어), 마스터 데이터, 보유 데이터, 기록 데이터, 재화와 결제 데이터가 모든 게임에 존재한다. 차이는 이 중 어느 영역에 데이터가 집중되는가에 있다. LoL은 매치 기록, 메이플스토리는 아이템과 옵션, 원신은 캐릭터 육성과 기원 기록, 클래시 로얄은 카드, 대전, 클랜 데이터가 중심이다.

화면에 표시되는 정보만으로도 개체와 관계의 상당 부분을 도출할 수 있었다. 특히 M:N 관계를 연결 테이블로 분해하는 방법은 4종 모두에서 반복적으로 적용되었다.

설계 과정의 주요 쟁점은 데이터를 어느 수준까지 별도 테이블로 분리할 것인가였다. 메이플스토리의 잠재능력 옵션을 컬럼으로 둘지 테이블로 분리할지, 원신의 천장 횟수를 배너별로 저장할지 기원 종류별로 저장할지가 그 예이다. 이러한 판단은 해당 데이터를 어떤 조건으로 조회하고 갱신하는지를 기준으로 결정하였다. 또한 클래시 로얄의 대전 기록처럼 과거 시점의 값을 보존해야 하는 경우에는 정규화보다 스냅샷 저장이 적합하다.
