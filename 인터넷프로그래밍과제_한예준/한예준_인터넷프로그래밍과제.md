# 2026학년도 인터넷프로그래밍 중간고사 과제

**과제명:** 게임 데이터베이스 분석 포트폴리오 (MySQL Workbench 역추론 모델링)
**제출자:** 한예준

---

## 1. 서론

본 과제는 실제 상용 서비스 중인 3종의 게임(리그 오브 레전드, 붕괴: 스타레일, 브롤스타즈)을 선정하여, 게임 내 핵심 시스템과 과금 구조가 데이터베이스에 어떻게 설계되어 있을지 분석한 포트폴리오입니다.

---

## 2. [게임 1] 리그 오브 레전드 (League of Legends)

### 2.1 게임 시스템 및 과금 구조 분석

- **장르:** 5v5 세션(Match) 중심의 MOBA
- **인게임 재화:** 골드, 아이템은 세션 종료 시 소멸하는 휘발성 데이터이므로 별도 테이블 없이 제외 (매치 로그에는 KDA와 승패만 기록)
- **과금:** 인게임 밸런스에 영향을 주지 않는 '스킨' 중심
- **설계 핵심:** 유저와 챔피언/스킨 간의 소유권(N:M) 관리

### 2.2 핵심 개체(Entity) 및 속성 정의

**accounts (계정)**

| 컬럼 | 키 | 설명 |
|---|---|---|
| account_id | PK | 계정 고유 번호 (자동 증가) |
| nickname | UNIQUE | 소환사명 (8자 이내, 중복 불가) |
| level | | 계정 레벨 |
| rp | | 보유 RP (유료 재화) |
| blue_essence | | 보유 파랑 정수 (무료 재화) |

**champions (챔피언)**

| 컬럼 | 키 | 설명 |
|---|---|---|
| champion_id | PK | 챔피언 고유 번호 |
| name | | 챔피언 이름 |
| role | | 역할군 (탑, 정글, 미드 등) |
| be_price | | 파랑 정수 구매 가격 |
| rp_price | | RP 구매 가격 |

**skins (스킨)**

| 컬럼 | 키 | 설명 |
|---|---|---|
| skin_id | PK | 스킨 고유 번호 |
| champion_id | FK | 스킨이 속한 챔피언 |
| skin_name | | 스킨 이름 |
| rp_price | | RP 구매 가격 (스킨은 RP로만 구매) |
| tier | | 스킨 등급 (등급이 없으면 NULL) |

**user_champions / user_skins**: 유저와 상품 간의 N:M 관계를 해소하는 교차 테이블. 중복 소유를 방지하기 위해 복합 기본키(Composite PK)를 사용.

| 테이블 | 컬럼 | 키 | 설명 |
|---|---|---|---|
| user_champions | account_id | PK, FK | 챔피언을 보유한 계정 |
| | champion_id | PK, FK | 보유한 챔피언 |
| | mastery_point | | 해당 챔피언의 숙련도 점수 |
| user_skins | account_id | PK, FK | 스킨을 보유한 계정 |
| | skin_id | PK, FK | 보유한 스킨 |

**matches (매치 기본) & match_participants (참여 상세 로그)**: 한 세션에 10명이 참여하므로 분리 설계. 결과 분석을 위해 kills, deaths, assists, win_loss 기록.

| 테이블 | 컬럼 | 키 | 설명 |
|---|---|---|---|
| matches | match_id | PK | 매치 고유 번호 |
| | game_mode | | 게임 모드 (솔로랭크, 일반 등) |
| | game_duration | | 경기 진행 시간 (초) |
| | play_date | | 경기 일시 |
| match_participants | match_id | PK, FK | 참여한 매치 |
| | account_id | PK, FK | 참여한 계정 (매치당 한 번만 기록) |
| | champion_id | FK | 해당 매치에서 사용한 챔피언 |
| | skin_id | FK | 착용한 스킨 (기본 스킨이면 NULL) |
| | kills / deaths / assists | | 킬 / 데스 / 어시스트 수 |
| | win_loss | | 승패 (1: 승, 0: 패) |

## 3. [게임 2] 붕괴: 스타레일 (Honkai: Star Rail)

### 3.1 게임 시스템 및 과금 구조 분석

- **장르:** 수집형 턴제 RPG
- **핵심 시스템:** 확률형 뽑기(가챠/워프), 랜덤 옵션 장비(유물)
- **가챠:** 로그를 트랜잭션 단위로 보관, 천장(Pity) 시스템을 위한 누적 횟수 관리 필수
- **유물:** 획득 시마다 옵션이 다르므로 개별 인스턴스로 분리

### 3.2 핵심 개체(Entity) 및 속성 정의

**players (유저)**

| 컬럼 | 키 | 설명 |
|---|---|---|
| uid | PK | 유저 고유 UID |
| nickname | | 닉네임 |
| level | | 개척 레벨 |
| stamina | | 보유 개척력 (행동력) |
| stellar_jade | | 보유 별옥 (가챠 재화) |
| oneiric_shard | | 보유 몽상의 파편 (유료 재화) |
| created_at | | 가입 일시 |

**characters / user_characters**: 캐릭터는 중복 소유가 불가능하여 복합 PK 교차 테이블로 관리 (eidolon_level로 돌파 관리).

| 테이블 | 컬럼 | 키 | 설명 |
|---|---|---|---|
| characters | char_id | PK | 캐릭터 고유 번호 |
| | name | | 캐릭터 이름 |
| | element | | 속성 (물리, 화염 등) |
| | path | | 운명의 길 (파멸, 수렵 등) |
| | rarity | | 희귀도 (4성, 5성) |
| user_characters | uid | PK, FK | 캐릭터를 보유한 유저 |
| | char_id | PK, FK | 보유한 캐릭터 |
| | level | | 캐릭터 레벨 |
| | eidolon_level | | 돌파(성혼) 단계 (중복 획득 시 상승) |

**user_light_cones / user_relics**: 동일 장비 중복 소유가 가능하므로 개별 instance_id (PK)를 부여한 1:N 구조 설계. user_relics는 sub_stats_json을 통해 무작위 부옵션을 유연하게 저장.

| 테이블 | 컬럼 | 키 | 설명 |
|---|---|---|---|
| user_light_cones | instance_id | PK | 광추 개체 고유 번호 |
| | uid | FK | 광추를 보유한 유저 |
| | light_cone_id | FK | 광추 종류 |
| | level | | 광추 레벨 |
| | superimposition | | 중첩(재련) 단계 |
| user_relics | relic_instance_id | PK | 유물 개체 고유 번호 |
| | uid | FK | 유물을 보유한 유저 |
| | set_id | | 유물 세트 코드 |
| | slot_type | | 장착 부위 |
| | main_stat | | 주옵션 |
| | sub_stats_json | | 무작위 부옵션 (JSON으로 저장) |
| | level | | 유물 강화 레벨 |
| | equipped_char_id | FK | 장착 중인 캐릭터 (미장착이면 NULL) |

**gacha_banners / gacha_logs (가챠)**: 배너 정보와 뽑기 이력.

| 테이블 | 컬럼 | 키 | 설명 |
|---|---|---|---|
| gacha_banners | banner_id | PK | 배너 고유 번호 |
| | banner_name | | 배너(워프) 이름 |
| | start_date / end_date | | 배너 진행 시작 / 종료 일시 |
| gacha_logs | log_id | PK | 로그 고유 번호 |
| | uid | FK | 뽑기를 한 유저 |
| | banner_id | FK | 뽑기를 진행한 배너 |
| | item_type | | 획득한 대상의 종류 (캐릭터 / 광추) |
| | item_id | | 획득한 대상의 번호 (item_type에 해당하는 테이블 기준) |
| | pull_count | | 해당 배너의 누적 뽑기 횟수 (천장 계산 기준) |
| | pulled_at | | 뽑은 일시 |

**분석 포인트:** 배너별 누적 뽑기 횟수(`pull_count`)를 기록하여 5성 천장(확정 지급) 시스템의 기틀을 마련함.

## 4. [게임 3] 브롤스타즈 (Brawl Stars)

### 4.1 게임 시스템 및 과금 구조 분석

- **장르:** 캐주얼 모바일 슈팅
- **진척도:** 캐릭터(브롤러)별 독립적인 트로피 관리
- **능력 해금:** 가젯, 스타파워, 하이퍼차지, 버프
- **과금:** 시즌제 '브롤 패스(Brawl Pass)' 중심, 티어별 보상의 중복 수령 검증 구조 필요

### 4.2 핵심 개체(Entity) 및 속성 정의

**users (유저)**

| 컬럼 | 키 | 설명 |
|---|---|---|
| user_tag | PK | 유저 고유 태그 (문자열) |
| nickname | | 닉네임 |
| total_trophies | | 보유 총 트로피 |
| gems | | 보유 보석 (유료 재화) |
| coins | | 보유 코인 (무료 재화) |
| club_id | FK | 소속 클럽 (무소속이면 NULL) |

**clubs (클럽)**

| 컬럼 | 키 | 설명 |
|---|---|---|
| club_id | PK | 클럽 고유 번호 |
| club_name | | 클럽 이름 |
| required_trophies | | 가입에 필요한 최소 트로피 |
| president_tag | FK | 클럽장 유저 (users 참조) |

**brawlers (브롤러 메타)**

| 컬럼 | 키 | 설명 |
|---|---|---|
| brawler_id | PK | 브롤러 고유 번호 |
| name | | 브롤러 이름 |
| rarity | | 희귀도 |
| class_type | | 역할 클래스 (탱커, 암살자 등) |
| has_hypercharge | | 하이퍼차지 출시 여부 |
| has_buff_ability | | 버프 능력 출시 여부 |

**분석 포인트:** 신규 브롤러의 하이퍼차지 유무 및, 능력 출시 시 세트로 한 번에 업데이트되는 버프 시스템 특성을 고려해 메타 테이블에 플래그 부여.

**user_brawlers (소유/해금 상태)**

| 컬럼 | 키 | 설명 |
|---|---|---|
| user_tag | PK, FK | 브롤러를 보유한 유저 |
| brawler_id | PK, FK | 보유한 브롤러 |
| power_level | | 브롤러 파워 레벨 |
| brawler_trophies | | 해당 브롤러의 트로피 |
| gadget_slot | | 착용 중인 가젯 (0: 미착용, 1 / 2번) |
| star_power_slot | | 착용 중인 스타파워 (0: 미착용, 1 / 2번) |
| is_hypercharge_unlocked | | 하이퍼차지 해금 여부 |
| is_gadget_buff_unlocked | | 가젯 버프 해금 여부 |
| is_star_power_buff_unlocked | | 스타파워 버프 해금 여부 |
| is_hypercharge_buff_unlocked | | 하이퍼차지 버프 해금 여부 |

**분석 포인트:** 메타데이터 출시는 한 번에 이루어지지만, 인게임 해금은 독립적으로 진행됨. 이를 반영해 해금 여부를 개별 필드로 세분화하여 정교하게 저장.

**brawl_passes & pass_reward_claims**: 패스 티어별 중복 수령 방지를 위해 tier_level과 is_claimed 상태를 관리하는 이력 테이블 구성.

| 테이블 | 컬럼 | 키 | 설명 |
|---|---|---|---|
| brawl_passes | pass_id | PK | 패스 고유 번호 |
| | user_tag | FK | 패스를 가진 유저 |
| | season_number | | 패스 시즌 번호 |
| | is_plus_pass | | 유료(플러스) 패스 구매 여부 |
| | current_tier | | 현재 달성한 티어 |
| pass_reward_claims | claim_id | PK | 수령 이력 고유 번호 |
| | pass_id | FK | 해당 패스 |
| | tier_level | | 보상이 지급되는 티어 |
| | is_claimed | | 보상 수령 여부 (중복 수령 방지) |

## 5. 결론 및 비교 분석

3개의 게임은 장르와 과금 모델에 따라 데이터베이스 설계의 주안점이 달랐습니다.

| 구분 | 리그 오브 레전드 | 붕괴: 스타레일 | 브롤스타즈 |
|---|---|---|---|
| 설계 중심 | 매치 로그 | 개별 인스턴스 | 해금 / 진척도 |
| 과금 모델 | 스킨 구매 | 확률형 가챠 | 시즌제 패스 |
| 핵심 테이블 | match_participants | user_relics, gacha_logs | user_brawlers, pass_reward_claims |
| 설계 포인트 | 재화는 휘발 처리, 플레이 기록(KDA)과 영구 소유권(스킨) 위주로 정규화 | 랜덤 옵션(유물)과 천장 시스템을 위한 상세 트랜잭션 기록, 1:N 구조 | 강화 스킬 트리(버프, 가젯 등)의 독립적 해금 상태, 패스 보상 수령 여부 검증 |
