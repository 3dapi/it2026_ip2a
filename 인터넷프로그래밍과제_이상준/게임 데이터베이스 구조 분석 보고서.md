# 게임 데이터베이스 구조 분석 보고서

**분석 대상:** 슬레이 더 스파이어 · 스컬: 더 히어로 슬레이어

---

## 1. 슬레이 더 스파이어

### 1.1 게임 개요

플레이어는 캐릭터를 선택하고 맵의 노드(일반 전투, 엘리트, 이벤트, 상점, 휴식, 보물, 보스)를 선택하며 탑을 올라간다. 전투 보상과 상점에서 **카드, 유물, 포션**을 모아 덱을 강화하고, 최종 보스를 처치하면 승리한다. 한 번의 도전이 하나의 **런** 이다.

### 1.2 주요 시스템과 데이터 구조 분석

| 시스템 | 설명 | 필요한 데이터 | 대응 테이블 |
|---|---|---|---|
| 캐릭터 선택 | 캐릭터별 시작 체력·골드가 다름 | 캐릭터 이름, 시작 HP, 시작 골드 | `game_character` |
| 카드/덱 | 카드 종류·등급·비용, 강화 카드, 키워드(취약, 소멸 등) | 카드 정보, 원본-강화 관계, 키워드 | `card`, `keyword`, `card_keyword` |
| 유물 | 획득 시 지속되는 패시브 아이템 | 이름, 등급, 효과, 전용 캐릭터 | `relic` |
| 포션 | 소모성 아이템, 슬롯에 보관 | 이름, 등급, 효과 | `potion` |
| 전투 | 적과 조우 그룹 | 적 정보, 조우 구성, 막 | `enemy`, `encounter`, `encounter_enemy` |
| 이벤트 | 선택지가 있는 무작위 사건 | 이름, 막, 설명 | `game_event` |
| 맵 진행 | 노드를 방문하며 층을 오름 | 방문 층, 노드 유형, 종료 시점 HP·골드 | `run_floor` |
| 보상 | 전투 후 골드/카드/유물/포션 선택 | 보상 종류, 수량, 선택 여부 | `reward` |
| 상점 | 카드·유물·포션 구매 | 진열 상품, 가격, 구매 여부 | `shop_item` |
| 플레이 기록 | 계정, 한 판의 결과와 덱 구성 | 플레이어, 런, 덱·유물·포션 보유 내역 | `player`, `run`, `run_card`, `run_relic`, `run_potion` |

### 1.3 개체·속성·키 도출

**마스터 개체 (게임 정의 데이터)**

| 개체 | PK | FK | 주요 속성 |
|---|---|---|---|
| `game_character` | character_id | - | name, starting_hp, starting_gold |
| `card` | card_id | character_id (NULL=공용), base_card_id (자기 참조) | name, card_type, rarity, cost, is_upgraded, description |
| `keyword` | keyword_id | - | name, description |
| `card_keyword` | (card_id, keyword_id) | card_id, keyword_id | value |
| `relic` | relic_id | character_id (NULL=공용) | name, rarity, description |
| `potion` | potion_id | character_id (NULL=공용) | name, rarity, description |
| `enemy` | enemy_id | - | name, enemy_type, act, min_hp, max_hp |
| `encounter` | encounter_id | - | name, act |
| `encounter_enemy` | (encounter_id, enemy_id) | encounter_id, enemy_id | quantity |
| `game_event` | event_id | - | name, act, description |

**기록 개체 (플레이어 활동 데이터)**

| 개체 | PK | FK | 주요 속성 |
|---|---|---|---|
| `player` | player_id | - | nickname (유일값), created_at |
| `run` | run_id | player_id, character_id | ascension_level, current_gold, current_hp, max_hp, result, started_at, ended_at |
| `run_card` | run_card_id (대리키) | run_id, card_id | floor_acquired |
| `run_relic` | (run_id, relic_id) | run_id, relic_id | floor_acquired |
| `run_potion` | (run_id, slot_number) | run_id, potion_id | - |
| `run_floor` | run_floor_id | run_id, encounter_id (NULL), event_id (NULL) | floor_no, node_type, hp_after, gold_after |
| `reward` | reward_id | run_floor_id, card_id / relic_id / potion_id (각각 NULL) | reward_type, amount, is_picked |
| `shop_item` | shop_item_id | run_floor_id, card_id / relic_id / potion_id (각각 NULL) | item_type, price, is_purchased |

### 1.4 개체 간 관계와 카디널리티

| 관계 | 카디널리티 | 구현 방식 및 설명 |
|---|---|---|
| player – run | 1 : N | 한 플레이어가 여러 런을 진행. `run.player_id` |
| game_character – run | 1 : N | 런마다 캐릭터 하나 선택. `run.character_id` |
| game_character – card | 1 : N (선택) | 전용 카드는 캐릭터에 소속, `character_id`가 NULL이면 공용 카드 |
| game_character – relic / potion | 1 : N (선택) | 카드와 동일하게 NULL 허용 FK |
| card – card (강화) | 1 : N 자기 참조 (선택) | `base_card_id`로 강화 카드가 원본 카드를 참조. 논리적으로는 1:1에 가까움 |
| card – keyword | N : M | `card_keyword`로 분해. 카드 하나에 키워드 여러 개, 키워드 하나가 여러 카드에 사용 |
| encounter – enemy | N : M | `encounter_enemy`로 분해. `quantity`는 연결에 붙는 속성 |
| run – card | N : M | `run_card`로 분해. 같은 카드를 덱에 여러 장 넣을 수 있어 **대리키** 사용 |
| run – relic | N : M | `run_relic`로 분해. 유물은 중복 불가라 복합키 사용 |
| run – potion | N : M | `run_potion`로 분해. 슬롯 번호가 키의 일부 |
| run – run_floor | 1 : N | 런마다 방문한 노드 기록. (run_id, floor_no) 유일값 |
| run_floor – encounter | N : 1 (선택) | 전투 노드일 때만 값이 있음 |
| run_floor – game_event | N : 1 (선택) | 이벤트 노드일 때만 값이 있음 |
| run_floor – reward | 1 : N | 한 노드에서 여러 보상 가능 |
| run_floor – shop_item | 1 : N | 상점 노드의 진열 상품 |
| reward / shop_item – card, relic, potion | N : 1 (선택, 택1) | 종류에 맞는 하나의 FK만 값을 가짐 |

### 1.5 설계 판단과 분석

1. **공용/전용 데이터를 NULL 허용 FK로 표현했다.** `card.character_id`가 NULL이면 모든 캐릭터가 쓰는 공용 카드다. 공용을 위한 별도 "공용 캐릭터" 행을 만들지 않아 구조가 단순하다.
2. **자기 참조로 강화 카드를 표현했다.** 강화 카드를 별도 테이블로 분리하지 않고 `card.base_card_id`로 원본을 가리켜, 카드 정보 컬럼을 중복 정의하지 않는다.
3. **덱은 대리키, 유물은 복합키를 사용했다.** 같은 카드를 여러 장 가질 수 있는 덱(`run_card`)은 (run_id, card_id)가 유일하지 않으므로 `run_card_id`를 대리키로 두었고, 중복이 없는 유물(`run_relic`)은 복합키로 충분하다.
4. **현재 상태와 이력을 분리했다.** `run.current_hp/current_gold`는 현재 상태, `run_floor.hp_after/gold_after`는 노드별 스냅샷이다. 둘은 의도적으로 다른 시점의 값이므로 중복 저장이 아니라 이력 보존이다.
5. **보상·상점 상품은 "택1 FK" 구조다.** `reward`는 카드·유물·포션 중 하나만 값을 가진다. 구현이 단순한 대신 "정확히 하나만 NOT NULL" 제약을 DB가 강제하지 못한다(애플리케이션 또는 CHECK 제약으로 보완). 대안은 카드·유물·포션의 상위 테이블(`item_master`)을 두는 슈퍼타입 설계이며, 이 경우 구조는 더 엄격해지지만 조인이 늘어난다.
6. **정규화 상태.** 모든 속성은 원자값(1NF)이고, 복합키 테이블(`card_keyword`, `run_relic`, `run_potion`, `encounter_enemy`)의 비키 속성은 키 전체에 종속된다(2NF). 비키 속성 간 종속은 없다(3NF).

## 2. 스컬: 더 히어로 슬레이어

### 2.1 게임 개요

플레이어는 스컬(머리뼈)을 교체하며 전투하는 액션 플랫포머를 진행한다. 스테이지를 클리어할 때마다 **스컬, 아이템, 정수** 같은 보상을 얻고, 아이템의 **각인** 개수에 따라 추가 효과가 발동한다. 런에서 얻은 재화로 **영구 강화**를 올려 다음 런에 반영한다.

### 2.2 주요 시스템과 데이터 구조 분석

| 시스템 | 설명 | 필요한 데이터 | 대응 테이블 |
|---|---|---|---|
| 스컬 | 캐릭터 겸 무기. 등급·유형이 있고 스킬 2개와 교대 스킬 1개를 가짐. 상위 등급으로 진화 | 스컬 정보, 스킬, 진화 관계 | `skull`, `skill`, `skull_skill` |
| 아이템 | 능력치를 올리는 장비. 진화 가능 | 아이템 정보, 진화 관계 | `item` |
| 각인 | 아이템이 가진 속성. 같은 각인이 모일수록 효과 발동 | 각인, 아이템-각인 관계, 개수별 효과 | `inscription`, `item_inscription`, `inscription_effect` |
| 정수 | 쿨다운이 있는 액티브·패시브 효과 | 이름, 등급, 쿨다운, 효과 | `quintessence` |
| 스테이지 | 챕터와 스테이지 번호로 구성, 몬스터 등장 | 챕터·번호·유형, 등장 몬스터 | `stage`, `monster`, `stage_monster` |
| 상점 | 스테이지에 위치, 런마다 진열 상품이 다름 | 상점 유형, 런별 진열 상품 | `shop`, `run_shop_item` |
| 영구 강화 | 재화로 강화 레벨을 올려 계정에 누적 | 강화 종류, 레벨별 비용·효과, 플레이어별 레벨 | `upgrade`, `upgrade_level`, `player_upgrade` |
| 인벤토리 | 런 중 보유한 스컬·아이템·정수 슬롯 | 슬롯 번호, 보유 개체 | `run_skull_inventory`, `run_item_inventory`, `run_quintessence_inventory` |
| 클리어/보상 | 스테이지 클리어 기록과 보상 | 클리어 시간, 남은 HP, 보상 내역 | `stage_clear`, `reward` |
| 플레이 기록 | 계정과 한 판의 결과 | 플레이어, 런 | `player`, `run` |

### 2.3 개체·속성·키 도출

**마스터 개체 (게임 정의 데이터)**

| 개체 | PK | FK | 주요 속성 |
|---|---|---|---|
| `skill` | skill_id | - | name, cooldown, description |
| `skull` | skull_id | evolves_from_skull_id (자기 참조) | name, rarity, type, description |
| `skull_skill` | (skull_id, slot_type) | skull_id, skill_id | slot_type (SKILL1 / SKILL2 / SWAP) |
| `quintessence` | quintessence_id | - | name, rarity, cooldown, passive_effect, active_effect |
| `item` | item_id | evolves_from_item_id (자기 참조) | name, rarity, description |
| `inscription` | inscription_id | - | name, description |
| `item_inscription` | (item_id, inscription_id) | item_id, inscription_id | - |
| `inscription_effect` | effect_id | inscription_id | required_count, effect_desc (유일값: inscription_id + required_count) |
| `stage` | stage_id | - | name, chapter_no, stage_no, stage_type (유일값: chapter_no + stage_no) |
| `monster` | monster_id | - | name, monster_type, max_hp |
| `stage_monster` | (stage_id, monster_id) | stage_id, monster_id | quantity |
| `shop` | shop_id | stage_id | shop_type |
| `upgrade` | upgrade_id | - | name, category, max_level, description |
| `upgrade_level` | (upgrade_id, level) | upgrade_id | cost_dark_jewel, effect_value |

**기록 개체 (플레이어 활동 데이터)**

| 개체 | PK | FK | 주요 속성 |
|---|---|---|---|
| `player` | player_id | - | nickname (유일값), dark_jewel, created_at |
| `player_upgrade` | (player_id, upgrade_id) | player_id, upgrade_id | current_level |
| `run` | run_id | player_id | current_gold, current_hp, max_hp, earned_dark_jewel, result, started_at, ended_at |
| `run_skull_inventory` | (run_id, slot_number) | run_id, skull_id | - |
| `run_item_inventory` | (run_id, slot_number) | run_id, item_id | - |
| `run_quintessence_inventory` | (run_id, slot_number) | run_id, quintessence_id | - |
| `stage_clear` | clear_id | run_id, stage_id | clear_time_sec, hp_after, gold_after, damage_taken, cleared_at |
| `reward` | reward_id | clear_id, item_id / skull_id / quintessence_id (각각 NULL) | reward_type, amount, is_picked |
| `run_shop_item` | run_shop_item_id | run_id, shop_id, item_id / skull_id / quintessence_id (각각 NULL) | item_type, price, is_purchased |

### 2.4 개체 간 관계와 카디널리티

| 관계 | 카디널리티 | 구현 방식 및 설명 |
|---|---|---|
| player – upgrade | N : M | `player_upgrade`로 분해. 플레이어별 강화 레벨(`current_level`)을 속성으로 가짐 |
| upgrade – upgrade_level | 1 : N | **약한 개체**. `upgrade_level`은 (upgrade_id, level) 복합키로 상위 개체에 종속 |
| player – run | 1 : N | `run.player_id` |
| run – skull | N : M | `run_skull_inventory`로 분해. 슬롯 번호로 위치 구분 |
| run – item | N : M | `run_item_inventory`로 분해 |
| run – quintessence | N : M | `run_quintessence_inventory`로 분해 |
| skull – skull (진화) | 1 : N 자기 참조 (선택) | `evolves_from_skull_id` |
| item – item (진화) | 1 : N 자기 참조 (선택) | `evolves_from_item_id` |
| skull – skill | N : M | `skull_skill`로 분해. `slot_type`이 키에 포함되어 스컬당 슬롯별 스킬 하나로 제한 |
| item – inscription | N : M | `item_inscription`으로 분해 |
| inscription – inscription_effect | 1 : N | 각인 개수별 효과를 행으로 분리 |
| stage – monster | N : M | `stage_monster`로 분해. `quantity`는 연결 속성 |
| stage – shop | 1 : N | `shop.stage_id` |
| stage – stage_clear | 1 : N | 같은 스테이지를 여러 런에서 클리어 |
| run – stage_clear | 1 : N | 런마다 클리어 기록 |
| stage_clear – reward | 1 : N | 클리어 한 번에 여러 보상 |
| run – run_shop_item | 1 : N | 런별 상점 진열 기록 |
| shop – run_shop_item | 1 : N | 어느 상점의 상품인지 |
| reward / run_shop_item – item, skull, quintessence | N : 1 (선택, 택1) | 종류에 맞는 하나의 FK만 값을 가짐 |

### 2.5 설계 판단과 분석

1. **슬롯 기반 인벤토리는 (run_id, slot_number) 복합키다.** 스컬 2칸, 아이템 최대 9칸, 정수 1칸처럼 위치가 의미를 갖기 때문에 개체 ID가 아니라 슬롯 번호를 키로 삼았다. 슬롯 자리가 중복되지 않음을 DB가 보장한다.
2. **스컬 슬롯 종류를 키에 넣었다.** `skull_skill`은 (skull_id, slot_type)이 키이므로, 한 스컬이 SKILL1·SKILL2·SWAP 슬롯에 각각 정확히 하나의 스킬만 가질 수 있다. 단순 N:M 연결 테이블에 "구분 속성"을 키로 올린 설계다.
3. **각인 효과를 데이터로 정형화했다.** 효과를 `item.description` 텍스트에 넣지 않고 `inscription_effect(required_count, effect_desc)` 행으로 분리했다. "각인 N개 이상이면 발동"을 조건 쿼리로 계산할 수 있고, 효과 구간이 늘어도 컬럼 추가 없이 행만 추가하면 된다.
4. **파생 데이터는 저장하지 않는다.** 런별 "각인 개수"는 `run_item_inventory`와 `item_inscription`을 조인해 집계하면 나오므로 별도 컬럼으로 저장하지 않았다. 중복과 불일치를 막는 정규화 판단이다.
5. **영구 강화는 약한 개체로 설계했다.** `upgrade_level`은 (upgrade_id, level)이 키라서 `upgrade` 없이는 존재할 수 없다. 레벨별 비용과 효과를 `upgrade`에 컬럼으로 늘어놓지 않아 최대 레벨이 바뀌어도 구조 변경이 없다.
6. **상점은 마스터와 런 기록을 분리했다.** `shop`은 "어느 스테이지에 어떤 유형의 상점이 있는가"라는 고정 정보, `run_shop_item`은 런마다 달라지는 진열 상품이다. 변하는 데이터와 변하지 않는 데이터를 나눈 설계다.
7. **정규화 상태.** 복합키 테이블의 비키 속성은 모두 키 전체에 종속(2NF)되고, 비키 속성 간 이행 종속이 없다(3NF). `reward`, `run_shop_item`의 택1 FK 구조는 슬더스와 같은 트레이드오프를 가진다.

## 3. 두 게임의 DB 구조 비교·분석

### 3.1 구조 비교표

| 비교 항목 | 슬레이 더 스파이어 | 스컬 |
|---|---|---|
| 테이블 수 | 18개 | 23개 |
| 장르 | 덱 빌딩 로그라이크 | 액션 플랫포머 로그라이트 |
| 진행 모델 | 맵에서 노드를 **선택**하며 진행 | 챕터·스테이지가 **고정된 순서**로 진행 |
| 진행 기록 테이블 | `run_floor` (노드 유형 `node_type`으로 전투·이벤트·상점 등을 한 테이블에서 표현) | `stage_clear` (클리어한 스테이지만 기록) |
| 캐릭터 개념 | `game_character` 테이블이 존재 | 별도 캐릭터 없이 `skull`이 캐릭터 역할 |
| 핵심 수집 개체 | 카드, 유물, 포션 | 스컬, 아이템, 정수 |
| 인벤토리 방식 | 덱은 **대리키**(중복 허용), 유물은 복합키, 포션은 슬롯 | 스컬·아이템·정수 모두 **슬롯 복합키** |
| 효과 표현 | 설명 텍스트 중심 (`description`), 카드 키워드는 N:M | 각인과 효과를 **정형 테이블**로 분리 |
| 자기 참조 관계 | `card.base_card_id` (카드 강화) | `skull`, `item`의 `evolves_from_*` (진화) |
| N:M 연결 테이블 | `card_keyword`, `encounter_enemy` | `skull_skill`, `item_inscription`, `stage_monster` |
| 메타 진행(영구 성장) | 없음 | `upgrade`, `upgrade_level`, `player_upgrade` |
| 상점 구조 | `shop_item`이 `run_floor`에 직접 연결 | `shop`(마스터) + `run_shop_item`(런 기록) 분리 |
| 재화 | 골드 하나 (런 내부) | 골드(런 내부) + dark_jewel(계정 누적) |

### 3.2 공통점

1. **마스터/기록 이중 구조.** 두 게임 모두 게임 정의 데이터(카드, 스컬, 스테이지 등)와 플레이어 활동 데이터(`run`, 인벤토리, 보상)를 분리한다. 마스터는 변하지 않고, 기록은 플레이마다 누적된다.
2. **`player → run` 중심 구조.** 플레이어 한 명이 여러 런을 가지며(1:N), 모든 기록 테이블이 `run`을 기준으로 연결된다.
3. **N:M 관계의 연결 테이블 분해.** 개체 간 다대다 관계는 모두 연결 테이블로 풀었고, 연결 자체에 속성이 있으면 거기에 둔다(`value`, `quantity`, `floor_acquired`).
4. **택1 FK 패턴.** `reward`가 여러 종류의 개체를 참조하기 위해 NULL 허용 FK를 병렬로 둔 구조가 같다.
5. **자기 참조로 단계 관계 표현.** 강화·진화처럼 "원본이 있는 개체"를 같은 테이블 안의 FK로 표현한다.

### 3.3 차이점과 그 원인

| 차이 | 원인 분석 |
|---|---|
| 슬더스는 `run_floor` 하나로 전투·이벤트·상점을 모두 기록하고, 스컬은 `stage_clear`가 클리어만 기록 | 슬더스는 플레이어가 **경로를 선택**하므로 어떤 노드를 방문했는지가 핵심 데이터다. 스컬은 경로가 고정이라 "어떻게 클리어했는가"(시간, 받은 피해)가 핵심 데이터다 |
| 슬더스 덱은 대리키, 스컬 인벤토리는 슬롯 키 | 슬더스의 덱은 **개수**가 중요하고 위치는 의미가 없다. 스컬은 장착 **위치**가 곧 규칙(슬롯 수 제한)이다 |
| 스컬만 각인 효과를 정형 테이블로 분리 | 스컬은 각인 개수에 따라 효과가 구간별로 발동하는 **조건부 규칙**이 있어 데이터로 표현해야 계산이 가능하다. 슬더스 유물은 대부분 단일 효과라 텍스트로 충분하다 |
| 스컬만 메타 진행 테이블이 있음 | 스컬은 런을 거듭하며 계정에 성장이 누적된다. 슬더스는 한 런이 독립적이다 |
| 스컬은 상점을 마스터/기록으로 분리 | 스컬의 상점은 스테이지에 고정된 시설이고 진열 상품만 런마다 바뀐다. 슬더스의 상점은 맵 노드 하나이므로 `run_floor`에 연결하는 편이 자연스럽다 |

### 3.4 종합 분석

두 게임의 DB 구조는 같은 "로그라이크 런 기록"이라는 뼈대를 공유하지만, **게임의 핵심 규칙이 데이터 구조를 결정**한다는 점이 뚜렷하게 드러난다. 선택형 맵과 덱 구성 규칙은 `run_floor`와 대리키 덱으로, 슬롯 장착과 각인 효과 규칙은 슬롯 복합키와 정형 효과 테이블로 표현되었다. 즉, 정규화와 키 설계는 이론적 규칙이 아니라 **"무엇이 유일해야 하고, 무엇이 중복될 수 있는가"를 게임 규칙에서 읽어내는 작업**이다.
